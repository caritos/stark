# Native iOS app: per-feature behavior notes

<!-- Moved verbatim from CLAUDE.md on 2026-11-12 to keep that file short. -->

Read the paragraph for a feature before changing it. The core rules (storage, agenda architecture, overdue semantics, theme, testing and deploying) stay in `CLAUDE.md`.

**Completion history** (`Reminder.completedAt`, `Reminder.seriesID`, `EventOutcomeRecord.recordedAt`, `CompletionHistory`, `AgendaItem.completionNote`): the store stamps `completedAt` (when it was ticked, distinct from `completedDate`, the occurrence's due date) on every completed copy, `seriesID` (the master's id, so a series' completions can be grouped) and `recordedAt` on each attended/skipped mark; all three are optional extra `X-STARK-*` `.ics` properties, absent on older records. `CompletionHistory.forReminder(_:among:today:)` / `.forEvent(_:today:)` produce `entries` (`CompletionEntry{due, done, daysLate}`) plus `doneLast30`, `doneLast90`, `lateLast90`, `lastDone`, `averageGapDays`, `longestGapDays`; records without a timestamp count by due date and are never "late". A completed row whose `completedAt` day differs from its due day shows "done Oct 14" as its time line (`completionNote`). `EditItemView` has a **History** section (counts, last done, gaps, the latest 10 entries) shown only when there are entries.

**Checkbox: 2.5 s undo window** (`Planner/PendingCompletions.swift`, mirrors Expo's `usePendingDone`): tapping an incomplete reminder's checkbox makes it *look* complete immediately (filled check, struck-through) but only commits after 2.5 s; tapping again inside the window cancels; tapping a completed reminder's checkbox un-completes immediately (no window); everything pending is flushed (committed, never dropped) whenever the scene leaves `.active`. Pending state is keyed by the row's stable `AgendaItem.id`, never a list position (Expo hit the bug where a delete renumbered rows and the timer completed the wrong task). Time is injected (`PendingScheduler`) so tests never sleep. Events have no checkbox (a tap anywhere on an event row opens the detail sheet).

**Event attendance** (`Event.outcomes`, `PlannerStore.setEventOutcome`, `AgendaItem.outcome`, `EventOutcomeActions`): the user can mark each occurrence of an event *attended* or *skipped* from the detail sheet (buttons worded like a reminder's: "Done" = attended, "Skip" = didn't attend, "Undo" = clear; the row's accessibility text still says attended/skipped); the row shows a filled ✓ marker (attended) or an outlined ✗ marker (skipped), and in both cases a dimmed, struck-through title like a completed reminder (the marker says which). The mark is stored on the event itself as one `X-STARK-ATTENDED:` / `X-STARK-SKIPPED:` line per occurrence (after the `EXDATE` lines; `;VALUE=DATE` for all-day events), in `recurring.ics` for a series and the month file for a one-off, so it never creates a copy and never removes the occurrence. Records are matched to occurrences by **calendar day** (like `exceptionDates`), so editing a time of day keeps them, while moving an event's start day orphans the old marks (harmless, not migrated). This is deliberately not the same as **"Remove This Occurrence"** (recurring events only, formerly "Skip This Occurrence"), which adds an exception date and makes the occurrence disappear. Reminders' button is also just "Skip" (it exdates the occurrence). The TypeScript converter never emits these lines (todo.txt has no equivalent). Re-importing a fresh `t export-ics` output into the app's Documents overwrites same-named month files, so it discards native-side edits including these marks; treat the app's files as the live copy once marks exist. `AgendaBuilder`'s `sortGroup` treats an event with a non-nil `outcome` as done for sorting too, the same as a completed reminder (`isCompleted || outcome != nil`) — `AgendaItem.isCompleted` is hardcoded `false` for every event (see its own doc comment), so without the `outcome` check an attended/skipped event stayed stuck in the normal (not-yet-done) sort position even though the row already rendered it dimmed and struck through, same as a completed reminder.

**Converting an event to a task and back (issue #116, 2026-11-01):** Edit shows the same pinned Event / Reminder `KindSwitch` as Add, for an event or an OPEN reminder (a completed reminder, including a series' completed copy, shows no switch). Switching changes the form's fields at once (Ends/Location/URL vs Priority) but nothing is stored until Save; Cancel discards. Save makes ONE store call, `PlannerStore.convertEvent(id:to:)` / `convertReminder(id:to:)` (convenience `convertToReminder(eventID:)` / `convertToEvent(reminderID:today:)`), which replaces the item under the SAME id: removed from its file, placed where the new kind routes it (`recurring.ics` for a recurrence, else the due/start month), each affected file written once; an unreadable destination month aborts with nothing changed; a completed reminder returns false. Rules are in `ItemConversion` (`Models/ItemConversion.swift`). Event -> task keeps title, notes, start (as the due date/time; all-day = due at start of day), recurrence (until/count) and exception dates; drops the end; appends "Location: x" / "URL: y" lines to the notes (after a blank line when there are notes; blank values skipped; the form footer says so); attended/skipped marks are dropped, and when there are any the tap on Reminder first asks (an alert naming the count; Cancel keeps it an event), on the tap rather than on save so the user knows before editing further. Task -> event keeps title, notes, due date (no time / 00:00 -> all-day event, otherwise timed with no end), recurrence and exception dates; priority is dropped silently; an undated task lands all-day on the form's date. A recurring event whose start is in the past becomes a task showing one carried overdue row (its first unresolved miss within the 90-day lookback), as the overdue rules above say. A recurring item converts as a whole series; its completed copies stay as history (they still carry `seriesID`, so the new event's History section no longer shows them). Plan blocks that pointed at a converted task are kept as harmless orphans (plans only ever match reminder rows). While converting, the per-occurrence actions and History are hidden (only Delete stays). Done: unit-tested (`ItemConversionTests`, `PlannerStoreConversionTests`), verified on an iPhone 17 Pro Max simulator (switch, marks alert incl. Cancel, recurring event -> task with Location/URL in notes, task -> event, files on disk, relaunch). Not yet verified on device; the "no switch on a completed reminder" case was not exercised visually. Observed: right after saving a conversion that collapses many agenda rows into one (daily event -> carried task), the agenda kept a stale scroll offset until relaunch (likely the same for any edit that shrinks the list a lot; not investigated). Deferred: converting from the agenda row, bulk conversion, undo, labelling the switch "Task".

**Last day of the month (issue #112, 2026-10-31):** Custom repeat -> On Days has a top row "Last day of the month", stored as `byMonthDay` `-1` (counts back from the month's end in `OccurrenceExpander`; combines with numbered days; summary reads "... on the last day"). Halloween is yearly + October + Last day. A lone `BYMONTHDAY=-1` decodes as a positional Last/Day entry (`RRuleCodec`), so `CustomRepeatView.init` maps that back to `byMonthDay: [-1]` to show it under On Days. There is deliberately NO "Last Day of Month" preset in the Repeat list (it read as ambiguous: which month?). **Add screen type switch (issue #109, 2026-10-31):** Event / Reminder is a `KindSwitch` in `AddItemView` (two flat 48 pt tap targets, chosen one accent-filled) pinned above the form with `safeAreaInset`, replacing the stock segmented control; the title is inline. `KindSwitch` lives in its own file (`KindSwitch.swift`, with `ItemKind`) and Edit shows it too, to convert the item (issue #116, paragraph above). **Add/edit fields** (`AddItemView`, `EditItemView`; logic in `ReminderPriority`, `FormFields`, `EventSchedule`, `Event.rescheduled(to:allDay:)`, `Event.scheduled(start:end:allDay:)`): both screens have an **All day** toggle (date-only: reminders store start-of-day — the model's "no time" marker — and events set `isAllDay`; the toggle only normalises on save, so turning it on then off restores the picked time; switching an event from timed to all-day drops its `end`; from all-day to timed the Ends picker starts equal to Starts (which stores as no end) until the user sets one), **Notes** (reminders and events; blank saves as none), **Location** (events), **repeat end** (see the next paragraph), **URL** (events) and a three-level **Priority** picker (reminders only — events never carry a priority): `!` low = `PRIORITY:9`, `!!` medium = 5, `!!!` high = 1, None writes no line. An existing value maps to the nearest level (1-4 high, 5 medium, 6-9 low) and is only rewritten if the level is changed (`ReminderPriority.updated`). Timed events get **Starts**/**Ends** pickers (all-day events show no Ends picker): a new event defaults to one hour, moving the start moves the end by the same amount, and an end at or before the start is stored as no end (`EventSchedule.storedEnd`), so opening and saving an event without an end does not give it one; `Event.scheduled(start:end:allDay:)` applies the form. The agenda row shows the marks in the accent colour as a prefix before an incomplete reminder's title; sorting does not use priority. Undated reminders, lists, location-based reminders, alerts, time zones and calendars are deliberately not built (an undated reminder would be invisible: the agenda only lists dated items). A reminder due at exactly 00:00 is indistinguishable from a date-only one, so it reads back as All day. Saving trims surrounding whitespace from Notes and Location (imported values included), and an event whose stored end is at or before its start loses that end on save.

**Month grid density is now up to five calendar-colour dots plus a check glyph for reminders (stage 2 of the Fantastical redesign, 2026-11-16; `DayDensity.eventColors`); the rest of this paragraph describes the earlier two-hairline design (issue #110, 2026-10-31): the original dot markers were useless to the user and a cell tint looked bad, so each day gets a purple line (events) over an accent line (tasks), each a third / two thirds / full width of the number for 1 / 2-3 / 4+ items. Anything below about 'markers' now means these lines.** **Month grid shows the neighbouring months' days** (`MonthGridView`; logic in `MonthGrid`, `GridDay`, `gridDensity`; issue #96): the grid is always 6 rows x 7 columns (42 cells, Sunday-first) and the cells before day 1 / after the last day are the neighbouring months' real dates, dimmed, with their density markers — like Fantastical. `MonthGrid.days(for:)` builds the cells and `MonthGrid.range(for:)` the whole date range they cover; `gridDensity` counts tasks/events per cell keyed by ISO date over that range, on the same `buildAgendaItems` as the agenda (an overdue reminder still counts only on today's cell, and only when today is inside the range). `MonthGridView` loads every month the grid touches with `store.loadMonths(covering: MonthGrid.range(for:))` — a neighbour cell whose month was never loaded would silently show no markers. Tapping a neighbour cell selects it and scrolls the agenda (`ContentView.selectDate`), but the grid stays on the current month; only the chevrons page. `dayDensity(month:)` is no longer used by the app (its tests remain). **Tapping the month title returns to today** (`MonthGridView.goToToday`): it selects today (the agenda scrolls there, re-centring its window if needed) *and* pages the grid back to today's month — the one tap that does page the grid, since unlike a day cell it is an explicit "take me back" (issue #96's no-paging rule is for day cells only). The title is a plain-looking button with an accessibility hint; it has no visible affordance.

**Week / month / year modes with a drag bar** (`CalendarMode`, `ModeHandle`, `MonthGridView`, `YearView`; logic in `CalendarMode`, `MonthGrid.weekRow`/`weekStepped`, `YearGrid`, `yearDensity`, `DayDensity.level`; issue #95): a thin flat bar between the grid and the agenda switches the screen between **week** (the grid collapses to the one week row containing the selected day; ‹ › step by a week via `onSelectDate`, so the agenda follows), **month** (the default) and **year** (a scrolling two-column grid of twelve mini-months, days with items as rounded squares in a heat ramp by `DayDensity.level` — 1 / 2-3 / 4+ items — pale yellow, amber, salmon (`Colors.heatLow/heatMedium/heatHigh`; since stage 3a 2026-11-16 events and tasks tint alike, replacing the purple/orange split of issue #102); today is a solid accent rounded square; neighbouring-month days dimmed and never tinted; pressing a day shows a magnified white preview (a UIKit zero-delay press recognizer per mini-month, because a SwiftUI DragGesture blocks the vertical scroll; `YearView.cellIndex` maps the touch) and releasing on it selects the day, returns to month mode and scrolls the agenda; the bar hamburger menu also leaves year via DayTicker). Dragging up collapses and down expands; the mode changes **on release** (`CalendarMode.afterDrag`: 30 pt of travel, or a predicted 100 pt fling), animated, not tracking the finger. Tapping the bar in year mode returns to month; VoiceOver gets the bar as an adjustable "Calendar view" element. `MonthGridView.visibleMonth` re-syncs to the selected day's month on every mode change (so month -> year -> month re-pages the grid to the selected day's month) and follows it while in week mode; in month mode selecting a day still never pages the grid (issue #96). `yearDensity` counts on the same `buildAgendaItems` as the grid (an overdue reminder counts on today's day only when today is in the year, so a past year shows no task tint for incomplete reminders — they are overdue-pinned to today, exactly the month grid's rule — only events and completed reminders; that is not a bug), and `YearView` loads all twelve months of the year with `store.loadMonths(covering: YearGrid.range(year:))`. In year mode `ContentView` keeps the grid and agenda in the hierarchy, hidden (opacity 0, not hit-testable, hidden from VoiceOver), under the opaque `YearView` — removing the agenda would lose its scroll position and make a day picked in the year scroll to today instead. The mode is not persisted. Not built: Fantastical's collapsed strip of only-event-days, live finger tracking, pinch to zoom.

**Scroll-synced calendar selection** (`AgendaView.onDayInView`, `MonthGridView.scrollPagingDate`; issue #101): scrolling the agenda continuously updates which day is selected in the grid, in both week and month mode — matching Fantastical. `AgendaView` tracks the row at the top of its list by recording which rows a list cell is displayed for (`onAppear`/`onDisappear` into `displayedRowIDs`) and taking the earliest in list order (`AgendaScrollTracking.topRowID`) — **not `.scrollPosition(id:)`, which never reports a position on a `List`** (the first implementation used it and silently did nothing; issue #101 was reopened and fixed once that was found on a simulator, since unit tests can't see it: verify scroll sync by swiping the agenda and watching the grid) — resolves it to a day via a row→day lookup that mirrors `makeRows`'s own id logic, and reports it (150ms-debounced, matching `YearView`'s density-recompute debounce) through `onDayInView` — suppressed for 300ms after a tap-driven `scrollRequest` (re-armed both when the scroll is requested and again inside the deferred `proxy.scrollTo` call, covering the request→scroll gap and the scroll→settle gap), so a tap's own resulting scroll (e.g. tapping a neighbouring-month day, which scrolls the agenda there without paging the grid — issue #96) is much less likely to be mistaken for a user scroll and page the grid by mistake — a timing heuristic, not a guarantee. `ContentView` always updates `selectedDate` from `onDayInView` (which alone pages week mode, since the week row already derives from `selectedDate`) and separately sets `scrollPagingDate` (a `GridPagingRequest`, token-tagged like `ScrollRequest` so scrolling back to an already-reported day still re-fires), which `MonthGridView` uses to page `visibleMonth` — but only in month mode, and only from this scroll-only property, never from a plain `selectedDate` change. This means scrolling and tapping now deliberately differ in month mode: scrolling pages the grid, tapping still never does (issue #96's rule is unchanged for taps). Scroll always wins over an independent chevron browse too: `MonthGridView.changeMonth` (the chevrons) pages `visibleMonth` without touching `scrollPagingDate` at all, and the token means a subsequent scroll back to any day — including one that equals the last-reported value — always re-pages the grid, snapping it back to the agenda's position rather than leaving it stuck on the chevron-browsed month. Year mode is unaffected — this feature doesn't touch `YearView`.

**Search** (`SearchView`, `PlannerFile.availableMonths`, `PlannerStore.loadAllMonths`): a second floating button next to Add opens full-history text search — unlike the agenda, which only shows what's currently loaded (today's display window plus whatever's been scrolled/tapped into), Search loads every month file that exists on disk the first time it appears, so it can find anything ever saved in Stark's own files, not just what's nearby in time (superseded in part 2026-11-15: Apple items are searched only within two years either side of today plus every open reminder, and an Apple event series is one row; see "Apple overlay and write-through"). `availableMonths()` discovers which month files exist by filename pattern (the app previously had no way to enumerate them at all); `loadAllMonths()` loads each one not already in memory, yielding to the main actor between files so a loading indicator can animate rather than the UI freezing. One unconditional case-insensitive substring match across title, notes, and location (events) or title and notes (reminders) — no field picker (a Fantastical-style Title/Notes/Location/All row was considered and dropped for simplicity). Results reuse `AgendaRowView` for display and open the existing `EditItemView` on tap, built directly from the matched `Event`/`Reminder` (not through occurrence expansion) — one row per stored record, and editing a recurring result edits its master series, same as everywhere else in the app. Sorted newest date first (`SearchResults.find`'s `displayDate` sort, descending) — there is no creation-timestamp field anywhere in the model or the `.ics` format, so "newest" means each result's own scheduled/occurrence date, not when it was added.

**Timeboxing / Plan view** (`PlanBlock`, `PlanLayout`, `DayPlanModel`, `PlanDraft`, `PlanAgenda`, `PlanRowText`, `PlannerStore.replacePlans`/`plans`, `PlannerView.swift`; spec `docs/superpowers/specs/2026-11-01-timeboxing-design.md`, plan `docs/superpowers/plans/2026-11-01-timeboxing.md`): a calendar-clock button on the Today and Tomorrow agenda headers opens a full-screen planner, a day timeline plus a tray of open tasks. The user drags tasks onto the timeline as blocks (default 30 min, snap 15 min, no overlaps between blocks, none crossing midnight), resizes by the bottom grip, can remove a block or rework a saved plan; the check saves, writing `X-STARK-PLAN` entries into that day's month `.ics` (a `PlanBlock` per planned occurrence: reminder id + occurrence + start + minutes). **A plan is separate from the due date**: it never changes a task's due date, recurrence or completion, and a missed task keeps its original due date. The agenda shows a planned task at its planned time as a range ("9:00 - 9:30") on the planned day with the original due as a secondary line, while the task's normal today/overdue row stays; planned tasks count in month and year density; deleting a task drops its plans (in loaded months); completing the task completes it as always. **A day's save keeps entries the planner does not show**: `PlanDraft(model:saved:)` retains the day's stored blocks that `DayPlanModel.blocks` leaves out (a completed task's entry, kept as the record, or one whose task's month is not loaded) and the view saves `draft.blocksToSave`, so saving never deletes them; retained blocks are not shown, do not count for `hasChanges` and do not block placement, except done blocks (below). **Done blocks stay on the timeline** (`DayPlanModel.doneBlocks`/`DoneBlock`/`doneCount`, `PlanDraft.done`; 2026-11-01): a plan on the day whose task is completed (a one-off by id, or a recurring occurrence's completed copy by `seriesID` and due day = the plan's occurrence day) is drawn dimmed with a checkmark and a struck-through title. It is read-only (no grip, no remove, no drag, a tap does nothing), always written back on save, and an obstacle: `PlanDraft` places, moves and grows other blocks around it. The header shows `3 DONE - 2 PLANNED` (`DayPlanModel.summary`; only when something is done, a 0 part left out). The agenda is unchanged: a completed task shows its normal completed row. **A planned far-dated one-off still shows**: the tray offers one-offs of any date, but `buildAgendaItems` only lists the agenda window (and the 90-day overdue lookback), so `applyPlans(..., reminders:)` synthesizes a planned row for a live plan that matched no row when its reminder is an open one-off due on the plan's occurrence day (overdue if due before today; recurring reminders are never synthesized); the agenda and the month/year density pass all reminders. `PlannerStore.loadMonth` also loads the month of each loaded plan's occurrence, so that reminder is in memory after launch. **Tray panes** (`DayPlanModel.trayPast`/`trayToday`/`trayFuture`, `TrayPane`; 2026-11-01): the tray is three panes, PAST | TODAY (TOMORROW when planning tomorrow) | FUTURE, split by each item's own `occurrence` day (an overdue row's missed date, never its pinned display date) against the planned day: PAST newest first, TODAY by occurrence then title, FUTURE soonest first; planning tomorrow, tasks due today are PAST. `tray` stays the union in its old order. A tab row with counts, a hint line and page dots; switched by tab or by swiping sideways (a paged `TabView`); the planner opens on the middle pane; the tray is 250 pt tall. **Tray membership**: open one-offs of any date plus a recurring series' single open row; tasks already due that day at a set time sit on the timeline instead. Multi-day and all-day events show in a banner. Events marked Skip (didn't attend) for that day are left out of the timeline and the banner so their slot reads as free (issue #117, 2026-11-01); attended ones stay. Plans may exist for any day from today on (the planner steps there with the header chevrons, see **Week planner** below); a plan on a day before today is only ever viewed, never edited or written (lapsed plans). Not in v1: timer/focus mode, non-task blocks, auto-schedule, "move unfinished".

**Week planner and past days** (`PlannerDays`, `PlanSession`, `DayHistory` in StarkKit; `PastDayView`, `PlannerView.swift`; spec `docs/superpowers/specs/2026-11-02-week-planner-design.md`, plan `docs/superpowers/plans/2026-11-02-week-planner.md`; replaces the 2026-11-01 History screen, whose `DayHistoryView` and History button are gone, spec `docs/superpowers/specs/2026-11-01-plan-history-design.md` is historical): the planner header has ‹ › chevrons that step the viewed day by day with no upper limit; `PlannerDays` holds the stepping, the editable rule (today and later) and the month load range. A past day is viewed in the planner itself, view only: `DayHistory.make`/`weekStats` (reading `store.events`/`reminders`/`plans`; a plan whose reminder is gone is ignored) supply the numbers and `PastDayView` draws them read-only, reusing the planner's look (events and a banner, done blocks dimmed with a check and struck title, open blocks outlined in the accent with MISSED), with `PastDayHeader` under the title showing `2 DONE - 1 MISSED`, `3h planned - 2h done - 67%` (or `NO PLAN`) and the Sunday-Saturday week line; the date line says `- VIEW ONLY`, there is no tray, no gesture, no block menu and no check. `today` comes from the app (never `Date()`). **Per-day drafts**: `PlanSession` keeps one `PlanDraft` per edited day, stashed when stepping away and restored when stepping back; the check saves every changed day (`PlanSession.saveAll`, `store.replacePlans(on:with:)` per day, which now returns `Bool`; a failed day stays open with its draft kept, an inline error banner names the days, and a retry rewrites the saved ones identically); the ✓ is disabled when no day has changes; the ✕ asks "Discard changes to this plan?" when any day has unsaved changes (with an `N days have unsaved changes` message when more than one); `dropLapsed(today:)` discards drafts for days that passed, called when saving, closing and when `today` changes at midnight (a viewed day that stopped being editable switches to the view-only body). **`plannedElsewhere`**: `DayPlanModel.make(..., plannedElsewhere:)` takes the task occurrences planned on another day (saved plans plus the session's other drafts), so an occurrence planned on one day leaves the other days' trays and cannot be planned twice. Nothing on a past day edits a plan or a task.

**Weekly Review** (`WeeklyReview`, `WeeklyReviewView`): a **Weekly Review** row in Settings (moved there from a floating button, issue #111, 2026-10-31) opens a sheet for one Sunday-Saturday week, with a Share button that sends `WeeklyReview.shareText()` (plain ISO-dated text of counts, completed and still-open lists) through the system share sheet: date range with ‹ › paging, "N done · M open", "Events attended: N", then Completed and Still open lists (`AgendaRowView` rows; tap opens `EditItemView`). It opens on *last* week on a Monday and the current week every other day (`defaultWeekStart`). `WeeklyReview.summary` runs `buildAgendaItems` over the week and buckets by each item's real `occurrence`, never the overdue-pinned `displayDate`, so a reminder missed Tuesday is open for Tuesday's week; the week range is start of Sunday to last second of Saturday, stepped with a `Calendar` (never `DateMath.date(from:)`). **"Completed this week" means *due* that week**, not ticked that week: the model stores the occurrence date as `completedDate`; a `completedAt` timestamp now exists (see Completion history) but the review still buckets by due date, deliberately. A recurring series (daily included) shows ONE open row carrying its first unresolved miss, so Weekly Review buckets it into the week of that first miss, not into the later weeks it has been carried through; the current week therefore shows no separate open row for days the series was carried. For weeks older than the 90-day lookback an open row can appear for that week's first miss, and resolving it clears only that occurrence. **The view must call `store.loadMonths(covering: WeeklyReview.loadRange(...))` (the week widened back to the lookback) on appear and on every paging**, or items in unloaded month files silently vanish. Verified on an iPhone 17 Pro simulator (sheet renders, empty data only); paging and populated lists were not exercised visually.

**Claude Code bridge (2026-11-07; spec `docs/superpowers/specs/2026-11-07-claude-code-bridge-design.md`)**: optional, off until paired; lets Claude Code on the Mac add reminders and events through a signed `stark://add?batch=...&sig=...` link, delivered with `xcrun devicectl device process launch --payload-url` (no network call by Stark). StarkKit `Bridge/`: `BridgeBatch` (the JSON shape, limits of 200 items / 500-char title / 5000-char notes, all-or-nothing conversion to `Event`/`Reminder`, `%label` appended to notes, times read in the phone's time zone), `BridgeCodec` (deflate + base64url, size guards before decoding, splitting into batches), `BridgeAuth` (HMAC over the transmitted bytes, verified before decompressing), `BridgeReplayGuard` (10 min old / 2 min future window, last 200 batch ids), `ClaudeBridge` (verify, replay check, then since 2026-11-15 `ItemRepository.addBatch` into Apple Calendar/Reminders, all or nothing, in the default calendar/list; banner text; the secret is read from the Keychain, `whenUnlockedThisDeviceOnly`; `handle` is async and serialized). Items are added immediately, no approval step (owner's decision). Idempotency is the sidecar's bridge ledger (`ItemSidecar.recordBridge`, bridge item id -> Apple identifier, written in one write right after the commit): ids already in the ledger are skipped, so re-sending a file adds only what was not added and an item deleted in Apple stays deleted ("Already added" when nothing is left). Without full Calendar/Reminders access, an unreadable sidecar or a missing default destination the batch is rejected with a banner and nothing is added (`PlannerStore.importItems` is no longer called). App glue: `StarkApp` (builds the bridge with the auto-updating calendar, the repository and the sidecar), `ContentView` (`onOpenURL`; a URL that arrives before the overlay and destinations are ready (`bridgeReady`) is queued there; the old local-store load gate was removed), `ClaudeCodeSettingsView` (Settings > Claude Code: status "Secret ready" because the app cannot know the Mac has it; show/copy secret on a local-only pasteboard item, Reset pairing). The Mac side is the SwiftPM executable `stark-claude` (`ios/Sources/stark-claude/main.swift`, logic in `StarkClaudeCore`: `pair`, `add`, `today`; Mac login Keychain; `DeviceResolver`; `PhoneLock` checks `devicectl device info lockState` before every batch because a locked phone silently drops the URL; ids are deterministic from item content so resending a file is idempotent). `today` is unavailable since 2026-11-15 (it prints "unavailable until the Mac tool", exit 0, and reads nothing: the old pull of `/Documents` would silently omit Apple items); `/stark` step 4 skips spreading items across days until the Mac tool exists. Install with `ios/scripts/install-stark-claude.sh` (tested by `install-stark-claude.test.sh`); the slash command is `.claude/commands/stark.md`. The CLI can only report "sent N of M batches", never "added".

**Settings** (`SettingsView`): a floating button, leftmost of the three (Settings, Search, Add — Add stays rightmost/closest to the corner as the primary action), opens an About-only screen: an **App Name** row (tappable, opens `https://stark.caritos.com`), a **Version** row (build number in parentheses), a **Developer** row (`http://caritos.com`), and Privacy Policy / Terms of Service / FAQ rows — App Name/Version read from `Bundle.main.infoDictionary` (never hardcoded, so they can't drift from the actual build). Privacy Policy and Terms of Service open the `web/` site's `/privacy` and `/terms` routes; **FAQ opens `FAQView`, a native in-app screen, not a link out to the website** — deliberately, so it works offline like the rest of the app. `FAQView` is a short, static, hand-maintained list of question/answer entries (currently just the `+`/`@`/`%`/`~` tagging convention) with no remote-fetch mechanism, matching the app's local-first stance; add entries to it directly as they come up, and keep the web site's own `/faq` page (a separate, parallel copy — see the `web/` section below) as what a browser visitor sees instead. ~~There's nothing configurable yet in Settings itself: storage is just the local Documents directory~~ (superseded 2026-11-15: Settings > Apple Calendar and Reminders holds the access status, the default calendar and list for new items and the calendar/list selection; Settings > Claude Code holds the bridge pairing; Stark's own older items still live in the local Documents directory).

**Tag autocomplete** (`TagAutocomplete`, `TagSuggestionRow`): while typing in Title, Notes, or Location (Add/Edit) or the Search field, a horizontal row of tap-to-complete chips appears under the field whenever its text ends in a `+project`/`@context`/`%label`/`~person`-prefixed partial word — e.g. typing `~s` suggests every already-used `~`-token starting with `s` (`~sophia`, `~sam`, …), scanned fresh from every loaded event/reminder's title and notes on every keystroke (no index; fine at this app's dataset sizes). None of the four sigils are parsed into a structured field anywhere in `Event`/`Reminder` — this is purely "help me re-type something I've already written elsewhere," ported from the same feature in the deprecated Expo app's `AddTaskModal` (`getTagPrefix`/`collectTags`). Like Search, the suggestion corpus is the user's whole history: `AddItemView` and `EditItemView` both call `store.loadAllMonths()` in `.task` (non-blocking — suggestions just improve as more months finish loading, the form is usable immediately). `TagAutocomplete.currentPrefix(in:)` only ever looks at the *last word* of the field's text, i.e. assumes the cursor is at the end — the same simplification the Expo version made, true for a normal append-as-you-type field and not worth actual cursor-position tracking for. `TagAutocomplete.applying(_:to:)` appends a trailing space so typing can continue right after the completed tag — except in `SearchView`, which trims it, since a trailing space would require the matched text to literally contain a space right after the tag (failing whenever the tag is the last word of a title/notes/location). The URL field deliberately does not get this: `%`/`@` mean something else entirely in a URL (`%20` encoding, a `mailto:` address), so suggesting a `~person` tag there would only be noise. **Keyboard sigil bar** (`SigilKeyboardBar`, `TagAutocomplete.appending`; issue #104): an opt-in row of one-tap `+` `@` `%` `~` buttons directly above the keyboard, so tags don't need the shift/symbol pages. **Off by default**, switched on in Settings → Keyboard (`SigilKeyboardSetting`, an `@AppStorage` bool; the toggle is hidden on Mac Catalyst, which has no on-screen keyboard, and the bar is compiled out there). It appends the sigil at the *end* of the focused field (Add: Title/Notes; Edit: Title/Location/Notes; Search), with a separating space, matching `currentPrefix`'s last-word-only assumption; cursor-position insertion would need UIKit-backed fields and wouldn't open suggestions anyway. A tap while the last word is already a bare sigil is a no-op. Hidden while the URL field is focused. **It is a bottom `safeAreaInset`, not a `ToolbarItemGroup(placement: .keyboard)`**: on iOS 26 the keyboard-placement row is drawn with no background (the form showed through it) and did not appear at all on a real iPhone. Not built: labelling the buttons by meaning (the app doesn't know a user's personal sigil meanings, e.g. `+` = location, `~` = person).

**Repeat End and event URL** (`RepeatEnd`, `RecurrenceRule.withoutEnd`, `Event.url`, `RepeatEndPickerView`; issue #97): a **Repeat End** row (Never / On Date / After N Times) appears under Repeat on add and edit, for events and reminders, only while Repeat is not Never. It maps onto `RecurrenceRule.until` (stored date-only at the start of its day, inclusive) and `count` (at least 1), which the `.ics` codec and `OccurrenceExpander` already honoured. **The screens hold the end as separate state** (`RepeatEnd`) and keep `recurrence` stripped of it (`withoutEnd`), applying it on save (`applied(to:)`), because `RepeatPickerView`'s presets replace the whole rule (which would wipe an end) and its checkmark compares whole rules; opening an item and saving it unchanged leaves its rule identical (pinned by `RepeatEndTests.unchangedRoundTrip`). For the same reason `CustomRepeatView` no longer has its own "Ends" section and never writes `count`/`until` (an end chosen there would have been silently replaced on save). Choosing Repeat = Never resets the end; an end date earlier than the start's day moves up to it (`clamped(toStartOn:)`). `count` counts the occurrences the rule *generates*, before exception dates are removed (`OccurrenceExpander` increments its match count before the exception-date filter), so a completed or skipped occurrence still consumes one of the N — RFC 5545-correct and what Apple Calendar does; a reminder set to "10 times" whose user skips three delivers seven. **Events have a URL** (`Event.url`, a plain unescaped `URL:` line after `LOCATION` and before `RRULE`, CR/LF stripped so a pasted value cannot inject a property line; no line when blank, so existing files and the migration fixtures are byte-identical); the edit sheet shows **Open Link** for an `http`/`https` URL. Reminders have no URL. Alerts, time zones and calendars are deliberately not built.

**Birthdays and anniversaries** (`Milestone`, `MilestoneTag`, `AgendaItem.milestone` in `Planner/Milestone.swift`; `AgendaRowView`): an *event* whose title or notes contain the whole tag `%birthday` or `%anniversary` (case-insensitive, trailing punctuation ignored; `%birthdays` doesn't count; a birthday wins if both) is shown with an emoji before its title (🎂 birthday, 🎉 anniversary — a prefix so it survives truncation) and a small secondary line under it: `Turns N` for a birthday, `N years` (`1 year`) for an anniversary. N is the occurrence's calendar year minus the event's original start year, so the event's own start date must be the birth/wedding date (as the todo.txt migration produces for yearly events); on the original date itself (N = 0) there is no note, only the emoji. Events only — a reminder tagged `%birthday` is not a milestone. Search results reuse the row, so they get the emoji and the age note too, computed for the date the result shows (a recurring event's result shows its next occurrence). Nothing was added to `EditItemView`, which edits the whole series and has no single age to show. VoiceOver's row summary says "birthday"/"anniversary" and the note.

**Mac Catalyst target** (`CalendarSidebar`; issue #100): the app also builds and runs as a Mac Catalyst destination of the same `Stark` target (`SUPPORTED_PLATFORMS` includes `maccatalyst`, `TARGETED_DEVICE_FAMILY = "1,2"` — Catalyst requires the iPad idiom even though no iPad-specific layout exists). `StarkKit` and almost every view are shared unchanged; the only differences are gated by `#if targetEnvironment(macCatalyst)`, the first platform-conditional code in this codebase. The window has a `480x520` minimum size (`StarkApp`, `.windowResizability(.contentSize)`) since the grid's fixed-height rows don't shrink with the window. ~~**Storage is local and independent per platform** — the Mac and iPhone builds show different data~~ (superseded 2026-11-15: both builds show and write the same Apple Calendar and Reminders data, synced by Apple; only Stark's older `.ics` items and its sidecar stay per device; Stark itself still adds no shared/iCloud storage of its own, decision 2026-09-23; issue #100 closed). **`OccurrenceExpander` keeps the anchor's time-of-day when it fast-forwards to the range**: the original fast-forward set `candidate = range.lowerBound`, so every occurrence carried the *range's* time (a 09:30 weekly reminder came back at 12:00 or 00:00) and the day/month/year differences used for `interval > 1` were computed from the wrong time, producing wrong-parity days (interval-2 daily/monthly/yearly). It now fast-forwards to `lowerBound`'s day at the anchor's time. Related trap: `DateMath.date(from:)` returns local **noon**, and `AgendaWindow`'s bounds used to be built from it, so `buildAgendaItems`' `displayRange.contains` silently dropped events before noon on the first day and after noon on the last. `range(around:)` and `loadRange(around:)` now run from the *start* of the first day to the last second of the last day (`startOfDay(day + 1) − 1 s`, stepped with a gregorian `Calendar` so DST days stay correct); never build inclusive day-range bounds from `DateMath.date(from:)`. Coupling to keep in mind: the future-range shortcut in `densityCounts` (`AgendaDensity.swift`, used by `gridDensity`/`yearDensity`) is only valid while `buildAgendaItems` uses `today` solely for the overdue cut-off/lookback; keep `YearDensityTests`' equivalence cases (which include interval > 1, count, until and non-noon anchors) in sync with any change there.

**Apple overlay and write-through** (2026-11-15; specs `docs/superpowers/specs/2026-11-15-apple-overlay-design.md` and `2026-11-15-apple-write-through-design.md`, spikes `2026-11-15-eventkit-write-spikes.md`): Apple Calendar and Reminders are the source of truth. Access is required: the overlay is always on (`AppleOverlayModel.isEnabled`), and while access is not granted `ContentView` shows `AccessRequiredView` above the grid (ALLOW ACCESS asks only from there; denied/write-only offers iOS Settings), local items stay visible below it and Add is disabled. Reading: the single merge point is `mergeAppleItems` (snapshot in, synthetic `AgendaItem`s out, ids `apple-...` never colliding with Stark's); `agendaWithApple` merges THEN applies plans (agenda, grid and year densities use it). One shared fetch window (`AppleFetchWindow`, the hull of the registered display/grid/search/planner/weeklyReview ranges) feeds the snapshot, `LatestReloadGate` makes a superseded reload wait for the newest fetch, and every write Stark makes reloads the overlay itself (`refreshAfterWrite`; `EKEventStoreChanged` is unreliable after a save). Apple reminders get the 90-day overdue lookback; date-only reminders behave as all-day; every open reminder is fetched (dated ones outside the window too). Undated reminders are not in the agenda: Search and the planner's NO DATE pane (`TrayPane.panes(for:)`) list them, a planned one appears on its planned day, the editor shows "No date" and Add Date (date-only, today). Writing: views call `ItemRouter` (Apple by the `apple-` id prefix, local otherwise); new items always go to Apple, in the default calendar/list (`DefaultDestinationModel`, Settings > Apple Calendar and Reminders, writable ones only; the default and any picked destination are always shown). Edit loads the real item (`router.details`) and writes a patch of only the changed fields diffed against `ItemDetails.formBaseline()`, never a stand-in saved whole; series edits go to the master (`.futureEvents`); a repeat Stark cannot represent is read-only text ("Custom, set in Calendar") and blocks converting; a rule change that would drop occurrences edited in Calendar asks first. Read-only: `AgendaItem.isReadOnly` = Apple source on a non-writable calendar; invitee-only events open read-only too (`AppleEditorState`); the read-only detail offers Open in Calendar/Reminders. Reminders: completing a repeating one is Apple's (EventKit advances it and leaves a completed copy; `complete` is idempotent per occurrence day); no Skip and no History for Apple items; uncompleting a series' completed copy is a notice only (`UncompleteNotice`). Events: Remove This Occurrence deletes that occurrence (`.thisEvent`); attended/skipped marks live in the sidecar (`Library/Application Support/Stark/sidecar.json`, `ItemSidecar`, also plan blocks for Apple reminders and the bridge ledger) and show in the editor, not on rows. Convert = create the other kind in the default destination + delete the original + remap plans (asks first when the event has attendees). Search: Apple events within +-2 years (registered only while Search is open), one row per series; all open reminders and completed ones in that window. Planner: Apple reminders in the tray, Done and saves through the router, a block whose occurrence the series has moved past reads DONE. Weekly Review: Apple reminders by completion day. Tag suggestions read the loaded snapshot. Day export includes Apple items because it exports what the agenda shows. Apple items are never copied into Stark's `.ics` files; Stark makes no network call. Never prune the selection while access is not granted or the calendar list is not loaded.
