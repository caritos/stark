# Native iOS app: per-feature behavior notes

<!-- Moved verbatim from CLAUDE.md on 2026-11-12 to keep that file short. -->

Read the paragraph for a feature before changing it. The core rules (storage, agenda architecture, overdue semantics, theme, testing and deploying) stay in `CLAUDE.md`. **Phase 3 (2026-11-17) removed Stark's own `.ics` store** (`PlannerStore`, `PlannerFile`, the ICS codec, month loading, the import and the "Not imported" mark): Stark now reads and writes only Apple Calendar and Reminders plus its sidecar. Where a paragraph below still describes the local store it says so; that text is history.

**Completion history: removed in phase 3 (2026-11-17).** `CompletionHistory` and the edit sheet's History section are gone: they read Stark's own `.ics` records (`X-STARK-*` stamps), and Apple items never had a history sheet. Still in the model: `Reminder.completedAt` (an Apple reminder's `completionDate`), `AgendaItem.completionNote` (a completed row whose completion day differs from its due day shows "done Oct 14" as its time line), `Reminder.seriesID` (only a completed copy's link to its series; Apple completed copies carry none) and `EventOutcomeRecord.recordedAt` (stamped by the sidecar on a mark).

**Checkbox: 2.5 s undo window** (`Planner/PendingCompletions.swift`, mirrors Expo's `usePendingDone`): tapping an incomplete reminder's checkbox makes it *look* complete immediately (filled check, struck-through) but only commits after 2.5 s; tapping again inside the window cancels; tapping a completed reminder's checkbox un-completes immediately (no window); everything pending is flushed (committed, never dropped) whenever the scene leaves `.active`. Pending state is keyed by the row's stable `AgendaItem.id`, never a list position (Expo hit the bug where a delete renumbered rows and the timer completed the wrong task). Time is injected (`PendingScheduler`) so tests never sleep. Events have no checkbox (a tap anywhere on an event row opens the detail sheet).

**Event attendance: can no longer be set.** The edit sheet's Done/Skip/Undo buttons for events were removed on 2026-11-15 (7d16605, Fantastical redesign), and phase 3 (2026-11-17) removed Stark's own `.ics` marks (`X-STARK-ATTENDED`/`X-STARK-SKIPPED`, now only in the old files). Marks saved earlier on Apple events stay in the sidecar (`ItemSidecar` outcomes, `ItemRouter.setEventOutcome`/`eventOutcome`, matched by calendar day, re-matched by external id) but nothing shows them: `AppleItemDetailView` loads the day's mark into the item it hands to `EditItemView`, which does not render it, and Apple agenda rows carry no outcome. The code keyed on `AgendaItem.outcome` (the row's dimmed, struck title with a check/cross marker, `sortGroup` treating it as done, the planner leaving a skipped event out of its timeline) is therefore inert. `EventOutcomeActions` now only decides whether **Remove This Occurrence** shows (recurring events), which deletes that one occurrence in Apple Calendar. Weekly Review's "Events attended" line was removed in phase 3 (spec decision 3).

**Converting an event to a task and back (issue #116, 2026-11-01; Apple-only since phase 3, 2026-11-17):** Edit shows the same pinned Event / Reminder `KindSwitch` as Add, for an event or an OPEN reminder (a completed reminder, including a series' completed copy, shows no switch). Switching changes the form's fields at once (Ends/Location/URL vs Priority) but nothing is stored until Save; Cancel discards. Save goes through `ItemRouter`: it creates the other kind in the DEFAULT calendar/list, deletes the original and remaps plan blocks (alarms, attendees and occurrences edited one by one are lost; it asks first when the event has attendees; refused for a repeat Stark cannot represent). Field rules are in `ItemConversion` (`Models/ItemConversion.swift`): event -> task keeps title, notes, start (as the due date/time; all-day = due at start of day), recurrence (until/count) and exception dates; drops the end; appends "Location: x" to the notes (after a blank line when there are notes; blank values skipped; the form footer says so) and the URL becomes the reminder's own link. Task -> event keeps title, notes, due date (no time / 00:00 -> all-day event, otherwise timed with no end), recurrence and exception dates; priority is dropped silently; an undated task lands all-day on the form's date. While converting, the per-occurrence actions are hidden (only Delete stays). (Until phase 3 Stark's own items converted in place in the `.ics` files under the same id, via `PlannerStore.convertEvent`/`convertReminder`, and dropped attended marks after asking; that path is gone.) Observed earlier: right after saving a conversion that collapses many agenda rows into one, the agenda kept a stale scroll offset until relaunch (not investigated). Deferred: converting from the agenda row, bulk conversion, undo, labelling the switch "Task".

**Last day of the month (issue #112, 2026-10-31):** Custom repeat -> On Days has a top row "Last day of the month", stored as `byMonthDay` `-1` (counts back from the month's end in `OccurrenceExpander`; combines with numbered days; summary reads "... on the last day"). Halloween is yearly + October + Last day. A lone month-day -1 can arrive as a positional Last/Day entry (from Apple through `RecurrenceDescriptor`; until phase 3 also from the `.ics` codec), so `CustomRepeatView.init` maps that back to `byMonthDay: [-1]` to show it under On Days. There is deliberately NO "Last Day of Month" preset in the Repeat list (it read as ambiguous: which month?). **Add screen type switch (issue #109, 2026-10-31):** Event / Reminder is a `KindSwitch` in `AddItemView` (two flat 48 pt tap targets, chosen one accent-filled) pinned above the form with `safeAreaInset`, replacing the stock segmented control; the title is inline. `KindSwitch` lives in its own file (`KindSwitch.swift`, with `ItemKind`) and Edit shows it too, to convert the item (issue #116, paragraph above). **Add/edit fields** (`AddItemView`, `EditItemView`; logic in `ReminderPriority`, `FormFields`, `EventSchedule`, `Event.rescheduled(to:allDay:)`, `Event.scheduled(start:end:allDay:)`): both screens have an **All day** toggle (date-only: reminders store start-of-day — the model's "no time" marker — and events set `isAllDay`; the toggle only normalises on save, so turning it on then off restores the picked time; switching an event from timed to all-day drops its `end`; from all-day to timed the Ends picker starts equal to Starts (which stores as no end) until the user sets one), **Notes** (reminders and events; blank saves as none), **Location** (events), **repeat end** (see the next paragraph), **URL** (events) and a three-level **Priority** picker (reminders only — events never carry a priority): `!` low = priority 9, `!!` medium = 5, `!!!` high = 1, None = no priority (Apple's reminder priority values). An existing value maps to the nearest level (1-4 high, 5 medium, 6-9 low) and is only rewritten if the level is changed (`ReminderPriority.updated`). Timed events get **Starts**/**Ends** pickers, quarter-hour only since 2026-11-17 (`QuarterHourDatePicker`, :00/:15/:30/:45; an item stored at an odd minute keeps it until the time is edited and shows "Saved time 10:07" under the row; a new item starts at the next quarter hour) (all-day events show no Ends picker): a new event defaults to one hour, moving the start moves the end by the same amount, and an end at or before the start is stored as no end (`EventSchedule.storedEnd`), so opening and saving an event without an end does not give it one; `Event.scheduled(start:end:allDay:)` applies the form. The agenda row shows the marks in the accent colour as a prefix before an incomplete reminder's title; sorting does not use priority. Undated reminders, lists, location-based reminders, alerts, time zones and calendars are deliberately not built (an undated reminder would be invisible: the agenda only lists dated items). A reminder due at exactly 00:00 is indistinguishable from a date-only one, so it reads back as All day. Saving trims surrounding whitespace from Notes and Location (imported values included), and an event whose stored end is at or before its start loses that end on save.

**Month grid density is now up to five calendar-colour dots plus a check glyph for reminders (stage 2 of the Fantastical redesign, 2026-11-16; `DayDensity.eventColors`); the rest of this paragraph describes the earlier two-hairline design (issue #110, 2026-10-31): the original dot markers were useless to the user and a cell tint looked bad, so each day gets a purple line (events) over an accent line (tasks), each a third / two thirds / full width of the number for 1 / 2-3 / 4+ items. Anything below about 'markers' now means these lines.** **Month grid shows the neighbouring months' days** (`MonthGridView`; logic in `MonthGrid`, `GridDay`, `gridDensity`; issue #96): the grid is always 6 rows x 7 columns (42 cells, Sunday-first) and the cells before day 1 / after the last day are the neighbouring months' real dates, dimmed, with their density markers — like Fantastical. `MonthGrid.days(for:)` builds the cells and `MonthGrid.range(for:)` the whole date range they cover; `gridDensity` counts tasks/events per cell keyed by ISO date over that range, on the same `buildAgendaItems` as the agenda (an overdue reminder still counts only on today's cell, and only when today is inside the range). `MonthGridView` registers `MonthGrid.range(for:)` with the Apple fetch window (`AppleFetchWindow`), so neighbour cells get their markers (until phase 3 it also loaded those months' `.ics` files with `store.loadMonths`). Tapping a neighbour cell selects it and scrolls the agenda (`ContentView.selectDate`), but the grid stays on the current month; only the chevrons page. `dayDensity(month:)` is no longer used by the app (its tests remain). **Tapping the month title returns to today** (`MonthGridView.goToToday`): it selects today (the agenda scrolls there, re-centring its window if needed) *and* pages the grid back to today's month — the one tap that does page the grid, since unlike a day cell it is an explicit "take me back" (issue #96's no-paging rule is for day cells only). The title is a plain-looking button with an accessibility hint; it has no visible affordance.

**Week / month / year modes with a drag bar** (`CalendarMode`, `ModeHandle`, `MonthGridView`, `YearView`; logic in `CalendarMode`, `MonthGrid.weekRow`/`weekStepped`, `YearGrid`, `yearDensity`, `DayDensity.level`; issue #95): a thin flat bar between the grid and the agenda switches the screen between **week** (the grid collapses to the one week row containing the selected day; ‹ › step by a week via `onSelectDate`, so the agenda follows), **month** (the default) and **year** (a scrolling two-column grid of twelve mini-months, days with items as rounded squares in a heat ramp by `DayDensity.level` — 1 / 2-3 / 4+ items — pale yellow, amber, salmon (`Colors.heatLow/heatMedium/heatHigh`; since stage 3a 2026-11-16 events and tasks tint alike, replacing the purple/orange split of issue #102); today is a solid accent rounded square; neighbouring-month days dimmed and never tinted; pressing a day shows a magnified white preview (a UIKit zero-delay press recognizer per mini-month, because a SwiftUI DragGesture blocks the vertical scroll; `YearView.cellIndex` maps the touch) and releasing on it selects the day, returns to month mode and scrolls the agenda; the bar hamburger menu also leaves year via DayTicker). Dragging up collapses and down expands; the mode changes **on release** (`CalendarMode.afterDrag`: 30 pt of travel, or a predicted 100 pt fling), animated, not tracking the finger. Tapping the bar in year mode returns to month; VoiceOver gets the bar as an adjustable "Calendar view" element. `MonthGridView.visibleMonth` re-syncs to the selected day's month on every mode change (so month -> year -> month re-pages the grid to the selected day's month) and follows it while in week mode; in month mode selecting a day still never pages the grid (issue #96). `yearDensity` counts on the same `buildAgendaItems` as the grid (an overdue reminder counts on today's day only when today is in the year, so a past year shows no task tint for incomplete reminders — they are overdue-pinned to today, exactly the month grid's rule — only events and completed reminders; that is not a bug), and `YearView` registers `YearGrid.range(year:)` with the Apple fetch window (until phase 3 it also loaded the year's `.ics` months). In year mode `ContentView` keeps the grid and agenda in the hierarchy, hidden (opacity 0, not hit-testable, hidden from VoiceOver), under the opaque `YearView` — removing the agenda would lose its scroll position and make a day picked in the year scroll to today instead. The mode is not persisted. **Full-screen Month (stage 3b, 2026-11-16)**: the menu's Month entry shows `FullMonthView` over the hidden DayTicker (a screen state like Year, not a `CalendarMode`): `monthLayout` (Kit) builds per-week bars, per-day lines and "N more..." from the same `buildAgendaItems`/`agendaWithApple` rows as the agenda; holiday chips are calendars whose title contains "holiday"; a day tap selects the day and returns to the DayTicker. **Full-screen Quarter (stage 3c, 2026-11-16)**: the menu's Quarter entry shows `FullQuarterView` (13 week rows from the first week of the displayed month, `QuarterGrid`; layout through `gridLayout`, the same engine as Month): colour bars without text, dots for timed events, red squares for reminders, month-start pills and seams; chevrons and swipe page one month; a day tap returns to the DayTicker. **Full-screen Day and Week (stage 4a, 2026-11-16)**: the menu's Day and Week entries show `FullDayView` / `FullWeekView` (read-only hour timelines, 60 pt per hour, `HourGrid`): `timelineLayout` (Kit) puts all-day and fully covered days as chips and timed events and timed reminders (30 minutes) as blocks clipped to the day, overlaps share columns; `timelineAgendaItems` builds the rows so a recurring reminder shows once; a block tap opens the agenda row's detail; a Week header tap opens the DayTicker on that day. Screen state is `FullScreenCalendar` (none, month, quarter, day, week). Not built: Fantastical's collapsed strip of only-event-days, live finger tracking, pinch to zoom.

**Scroll-synced calendar selection** (`AgendaView.onDayInView`, `MonthGridView.scrollPagingDate`; issue #101): scrolling the agenda continuously updates which day is selected in the grid, in both week and month mode — matching Fantastical. `AgendaView` tracks the row at the top of its list by recording which rows a list cell is displayed for (`onAppear`/`onDisappear` into `displayedRowIDs`) and taking the earliest in list order (`AgendaScrollTracking.topRowID`) — **not `.scrollPosition(id:)`, which never reports a position on a `List`** (the first implementation used it and silently did nothing; issue #101 was reopened and fixed once that was found on a simulator, since unit tests can't see it: verify scroll sync by swiping the agenda and watching the grid) — resolves it to a day via a row→day lookup that mirrors `makeRows`'s own id logic, and reports it (150ms-debounced, matching `YearView`'s density-recompute debounce) through `onDayInView` — suppressed for 300ms after a tap-driven `scrollRequest` (re-armed both when the scroll is requested and again inside the deferred `proxy.scrollTo` call, covering the request→scroll gap and the scroll→settle gap), so a tap's own resulting scroll (e.g. tapping a neighbouring-month day, which scrolls the agenda there without paging the grid — issue #96) is much less likely to be mistaken for a user scroll and page the grid by mistake — a timing heuristic, not a guarantee. `ContentView` always updates `selectedDate` from `onDayInView` (which alone pages week mode, since the week row already derives from `selectedDate`) and separately sets `scrollPagingDate` (a `GridPagingRequest`, token-tagged like `ScrollRequest` so scrolling back to an already-reported day still re-fires), which `MonthGridView` uses to page `visibleMonth` — but only in month mode, and only from this scroll-only property, never from a plain `selectedDate` change. This means scrolling and tapping now deliberately differ in month mode: scrolling pages the grid, tapping still never does (issue #96's rule is unchanged for taps). Scroll always wins over an independent chevron browse too: `MonthGridView.changeMonth` (the chevrons) pages `visibleMonth` without touching `scrollPagingDate` at all, and the token means a subsequent scroll back to any day — including one that equals the last-reported value — always re-pages the grid, snapping it back to the agenda's position rather than leaving it stuck on the chevron-browsed month. Year mode is unaffected — this feature doesn't touch `YearView`.

**Search** (`SearchView`, `SearchResults`, `SearchWindow`): a floating button opens text search over Apple data only (phase 3, 2026-11-17, spec decision 4): while Search is open it registers a range two years either side of today with the Apple fetch window, so it finds Apple events in that range (a repeating event is one row), every open Apple reminder in the shown lists (undated included) and completed reminders in the range. (Until phase 3 it also loaded every `.ics` month on disk, `PlannerStore.loadAllMonths`, to search Stark's whole own history; old Apple items beyond two years are not searchable now, a wider fetch is a later idea.) One unconditional case-insensitive substring match across title, notes, and location (events) or title and notes (reminders) — no field picker. Results reuse `AgendaRowView` and open the item's editor on tap; editing a recurring result edits its series. Sorted newest date first (`SearchResults.find`'s `displayDate` sort, descending): there is no creation timestamp in the model, so "newest" means each result's own scheduled/occurrence date.

**Timeboxing / Plan view** (`PlanBlock`, `PlanLayout`, `DayPlanModel`, `PlanDraft`, `PlanAgenda`, `PlanRowText`, `ItemRouter.replacePlans`/`plans(on:)`, `PlanCache`, `PlannerView.swift`; spec `docs/superpowers/specs/2026-11-01-timeboxing-design.md`, plan `docs/superpowers/plans/2026-11-01-timeboxing.md`): a calendar-clock button on the Today and Tomorrow agenda headers opens a full-screen planner, a day timeline plus a tray of open tasks. The user drags tasks onto the timeline as blocks (default 30 min, snap 15 min, no overlaps between blocks, none crossing midnight), resizes by the bottom grip, can remove a block or rework a saved plan; the check saves the day's `PlanBlock`s (reminder id + occurrence + start + minutes) to the sidecar (`Library/Application Support/Stark/sidecar.json`; until phase 3 Stark's own reminders' blocks went into that day's month `.ics` as `X-STARK-PLAN` lines). **A plan is separate from the due date**: it never changes a task's due date, recurrence or completion, and a missed task keeps its original due date. The agenda shows a planned task at its planned time as a range ("9:00 - 9:30") on the planned day with the original due as a secondary line, while the task's normal today/overdue row stays; planned tasks count in month and year density; completing the task completes it as always. **A day's save keeps entries the planner does not show**: `PlanDraft(model:saved:)` retains the day's stored blocks that `DayPlanModel.blocks` leaves out (a completed task's entry, kept as the record, or one whose task is not in the fetched Apple data) and the view saves `draft.blocksToSave`, so saving never deletes them; retained blocks are not shown, do not count for `hasChanges` and do not block placement, except done blocks (below). **Done blocks stay on the timeline** (`DayPlanModel.doneBlocks`/`DoneBlock`/`doneCount`, `PlanDraft.done`; 2026-11-01): a plan on the day whose task is completed (a one-off by id; for a repeating Apple reminder, a block whose occurrence the series has moved past reads done) is drawn dimmed with a checkmark and a struck-through title. It is read-only (no grip, no remove, no drag, a tap does nothing), always written back on save, and an obstacle: `PlanDraft` places, moves and grows other blocks around it. The header shows `3 DONE - 2 PLANNED` (`DayPlanModel.summary`; only when something is done, a 0 part left out). The agenda is unchanged: a completed task shows its normal completed row. **A planned far-dated one-off still shows**: the tray offers one-offs of any date, but `buildAgendaItems` only lists the agenda window (and the 90-day overdue lookback), so `applyPlans(..., reminders:)` synthesizes a planned row for a live plan that matched no row when its reminder is an open one-off due on the plan's occurrence day (overdue if due before today; recurring reminders are never synthesized); the agenda and the month/year density pass all reminders. **Tray panes** (`DayPlanModel.trayPast`/`trayToday`/`trayFuture`, `TrayPane`; 2026-11-01): the tray is three panes, PAST | TODAY (TOMORROW when planning tomorrow) | FUTURE, split by each item's own `occurrence` day (an overdue row's missed date, never its pinned display date) against the planned day: PAST newest first, TODAY by occurrence then title, FUTURE soonest first; planning tomorrow, tasks due today are PAST. `tray` stays the union in its old order. A tab row with counts, a hint line and page dots; switched by tab or by swiping sideways (a paged `TabView`); the planner opens on the middle pane; the tray is 250 pt tall. **Tray membership**: open one-offs of any date plus a recurring series' single open row; tasks already due that day at a set time sit on the timeline instead. Multi-day and all-day events show in a banner. Events marked Skip (didn't attend) for that day were left out of the timeline (issue #117, 2026-11-01); marks can no longer be set and Apple rows carry none, so this no longer happens (see Event attendance). Plans may exist for any day from today on (the planner steps there with the header chevrons, see **Week planner** below); a plan on a day before today is only ever viewed, never edited or written (lapsed plans). Not in v1: timer/focus mode, non-task blocks, auto-schedule, "move unfinished".

**Week planner and past days** (`PlannerDays`, `PlanSession`, `DayHistory` in StarkKit; `PastDayView`, `PlannerView.swift`; spec `docs/superpowers/specs/2026-11-02-week-planner-design.md`, plan `docs/superpowers/plans/2026-11-02-week-planner.md`; replaces the 2026-11-01 History screen, whose `DayHistoryView` and History button are gone, spec `docs/superpowers/specs/2026-11-01-plan-history-design.md` is historical): the planner header has ‹ › chevrons that step the viewed day by day with no upper limit; `PlannerDays` holds the stepping, the editable rule (today and later) and the Apple fetch range (`PlannerDays.loadRange`). A past day is viewed in the planner itself, view only: `DayHistory.make`/`weekStats` (reading the Apple snapshot and the sidecar's plans; a plan whose reminder is gone is ignored) supply the numbers and `PastDayView` draws them read-only, reusing the planner's look (events and a banner, done blocks dimmed with a check and struck title, open blocks outlined in the accent with MISSED), with `PastDayHeader` under the title showing `2 DONE - 1 MISSED`, `3h planned - 2h done - 67%` (or `NO PLAN`) and the Sunday-Saturday week line; the date line says `- VIEW ONLY`, there is no tray, no gesture, no block menu and no check. `today` comes from the app (never `Date()`). **Per-day drafts**: `PlanSession` keeps one `PlanDraft` per edited day, stashed when stepping away and restored when stepping back; the check saves every changed day (`PlanSession.saveAll`, the router's `replacePlans` per day, which returns `Bool`; a failed day stays open with its draft kept, an inline error banner names the days, and a retry rewrites the saved ones identically); the ✓ is disabled when no day has changes; the ✕ asks "Discard changes to this plan?" when any day has unsaved changes (with an `N days have unsaved changes` message when more than one); `dropLapsed(today:)` discards drafts for days that passed, called when saving, closing and when `today` changes at midnight (a viewed day that stopped being editable switches to the view-only body). **`plannedElsewhere`**: `DayPlanModel.make(..., plannedElsewhere:)` takes the task occurrences planned on another day (saved plans plus the session's other drafts), so an occurrence planned on one day leaves the other days' trays and cannot be planned twice. Nothing on a past day edits a plan or a task.

**Weekly Review** (`WeeklyReview`, `WeeklyReviewView`): a **Weekly Review** row in Settings (moved there from a floating button, issue #111, 2026-10-31) opens a sheet for one Sunday-Saturday week, with a Share button that sends `WeeklyReview.shareText()` (plain ISO-dated text of counts, completed and still-open lists) through the system share sheet: date range with ‹ › paging, "N done · M open", then Completed and Still open lists (`AgendaRowView` rows; tap opens the editor). The "Events attended" line was removed in phase 3 (2026-11-17, spec decision 3: always 0 for Apple events). It opens on *last* week on a Monday and the current week every other day (`defaultWeekStart`). While open it registers the week (`WeeklyReview.range(forWeekStarting:)`) with the Apple fetch window. Apple reminders count in the week they were COMPLETED; completed copies of repeating reminders count like one-offs. An open row is bucketed by its real `occurrence`, never the overdue-pinned `displayDate`. The week range is start of Sunday to last second of Saturday, stepped with a `Calendar` (never `DateMath.date(from:)`). (Until phase 3 Stark's own reminders counted by DUE date and the view loaded the week's `.ics` months via `WeeklyReview.loadRange`; both are gone.) Paging far back refetches events it never uses (parked).

**Claude Code bridge: removed 2026-11-17** (the owner decided he does not need it). The `stark://add` handler, Settings > Claude Code, the `stark-claude` Mac CLI and the `/stark` command are gone; the history is in git before that date and in `docs/superpowers/specs/2026-11-07-claude-code-bridge-design.md`. Old sidecar files may still carry a `bridgeLedger` key, which `ItemSidecar` ignores and drops on the next save.

**Settings** (`SettingsView`): a floating button, leftmost of the three (Settings, Search, Add — Add stays rightmost/closest to the corner as the primary action), opens an About-only screen: an **App Name** row (tappable, opens `https://stark.caritos.com`), a **Version** row (build number in parentheses), a **Developer** row (`http://caritos.com`), and Privacy Policy / Terms of Service / FAQ rows — App Name/Version read from `Bundle.main.infoDictionary` (never hardcoded, so they can't drift from the actual build). Privacy Policy and Terms of Service open the `web/` site's `/privacy` and `/terms` routes; **FAQ opens `FAQView`, a native in-app screen, not a link out to the website** — deliberately, so it works offline like the rest of the app. `FAQView` is a short, static, hand-maintained list of question/answer entries (currently just the `+`/`@`/`%`/`~` tagging convention) with no remote-fetch mechanism, matching the app's local-first stance; add entries to it directly as they come up, and keep the web site's own `/faq` page (a separate, parallel copy — see the `web/` section below) as what a browser visitor sees instead. ~~There's nothing configurable yet in Settings itself: storage is just the local Documents directory~~ (superseded 2026-11-15: Settings > Apple Calendar and Reminders holds the access status, the default calendar and list for new items and the calendar/list selection. Since phase 3, 2026-11-17, Stark no longer reads its older `.ics` files in Documents; they stay there untouched and there is no import row).

**Tag autocomplete** (`TagAutocomplete`, `TagSuggestionRow`): while typing in Title, Notes, or Location (Add/Edit) or the Search field, a horizontal row of tap-to-complete chips appears under the field whenever its text ends in a `+project`/`@context`/`%label`/`~person`-prefixed partial word — e.g. typing `~s` suggests every already-used `~`-token starting with `s` (`~sophia`, `~sam`, …), scanned fresh from the loaded Apple snapshot's titles and notes on every keystroke (no index; fine at this app's dataset sizes). None of the four sigils are parsed into a structured field anywhere in `Event`/`Reminder` — this is purely "help me re-type something I've already written elsewhere," ported from the same feature in the deprecated Expo app's `AddTaskModal` (`getTagPrefix`/`collectTags`). The corpus is whatever Apple data is currently fetched (the agenda window, plus two years either side while Search is open); until phase 3 Add/Edit also loaded every `.ics` month (`store.loadAllMonths()`) so it covered Stark's whole own history. `TagAutocomplete.currentPrefix(in:)` only ever looks at the *last word* of the field's text, i.e. assumes the cursor is at the end — the same simplification the Expo version made, true for a normal append-as-you-type field and not worth actual cursor-position tracking for. `TagAutocomplete.applying(_:to:)` appends a trailing space so typing can continue right after the completed tag — except in `SearchView`, which trims it, since a trailing space would require the matched text to literally contain a space right after the tag (failing whenever the tag is the last word of a title/notes/location). The URL field deliberately does not get this: `%`/`@` mean something else entirely in a URL (`%20` encoding, a `mailto:` address), so suggesting a `~person` tag there would only be noise. **Keyboard sigil bar** (`SigilKeyboardBar`, `TagAutocomplete.appending`; issue #104): an opt-in row of one-tap `+` `@` `%` `~` buttons directly above the keyboard, so tags don't need the shift/symbol pages. **Off by default**, switched on in Settings → Keyboard (`SigilKeyboardSetting`, an `@AppStorage` bool; the toggle is hidden on Mac Catalyst, which has no on-screen keyboard, and the bar is compiled out there). It appends the sigil at the *end* of the focused field (Add: Title/Notes; Edit: Title/Location/Notes; Search), with a separating space, matching `currentPrefix`'s last-word-only assumption; cursor-position insertion would need UIKit-backed fields and wouldn't open suggestions anyway. A tap while the last word is already a bare sigil is a no-op. Hidden while the URL field is focused. **It is a bottom `safeAreaInset`, not a `ToolbarItemGroup(placement: .keyboard)`**: on iOS 26 the keyboard-placement row is drawn with no background (the form showed through it) and did not appear at all on a real iPhone. Not built: labelling the buttons by meaning (the app doesn't know a user's personal sigil meanings, e.g. `+` = location, `~` = person).

**Repeat End and event URL** (`RepeatEnd`, `RecurrenceRule.withoutEnd`, `Event.url`, `RepeatEndPickerView`; issue #97): a **Repeat End** row (Never / On Date / After N Times) appears under Repeat on add and edit, for events and reminders, only while Repeat is not Never. It maps onto `RecurrenceRule.until` (stored date-only at the start of its day, inclusive) and `count` (at least 1), which `RecurrenceDescriptor` (Apple) and `OccurrenceExpander` honour. **The screens hold the end as separate state** (`RepeatEnd`) and keep `recurrence` stripped of it (`withoutEnd`), applying it on save (`applied(to:)`), because `RepeatPickerView`'s presets replace the whole rule (which would wipe an end) and its checkmark compares whole rules; opening an item and saving it unchanged leaves its rule identical (pinned by `RepeatEndTests.unchangedRoundTrip`). For the same reason `CustomRepeatView` no longer has its own "Ends" section and never writes `count`/`until` (an end chosen there would have been silently replaced on save). Choosing Repeat = Never resets the end; an end date earlier than the start's day moves up to it (`clamped(toStartOn:)`). `count` counts the occurrences the rule *generates*, before exception dates are removed (`OccurrenceExpander` increments its match count before the exception-date filter), so a completed or skipped occurrence still consumes one of the N — RFC 5545-correct and what Apple Calendar does; a reminder set to "10 times" whose user skips three delivers seven. **Events have a URL** (`Event.url`, Apple's event URL; until phase 3 also an `.ics` `URL:` line); the edit sheet shows **Open Link** for an `http`/`https` URL. Apple reminders keep a URL as their own link. Alerts, time zones and calendars are deliberately not built.

**Birthdays and anniversaries** (`Milestone`, `MilestoneTag`, `AgendaItem.milestone` in `Planner/Milestone.swift`; `AgendaRowView`): an *event* whose title or notes contain the whole tag `%birthday` or `%anniversary` (case-insensitive, trailing punctuation ignored; `%birthdays` doesn't count; a birthday wins if both) is shown with an emoji before its title (🎂 birthday, 🎉 anniversary — a prefix so it survives truncation) and a small secondary line under it: `Turns N` for a birthday, `N years` (`1 year`) for an anniversary. N is the occurrence's calendar year minus the event's original start year, so the event's own start date must be the birth/wedding date (as the todo.txt migration produces for yearly events); on the original date itself (N = 0) there is no note, only the emoji. Events only — a reminder tagged `%birthday` is not a milestone. Search results reuse the row, so they get the emoji and the age note too, computed for the date the result shows (a recurring event's result shows its next occurrence). Nothing was added to `EditItemView`, which edits the whole series and has no single age to show. VoiceOver's row summary says "birthday"/"anniversary" and the note.

**Apple Birthdays calendar (2026-11-17)**: an Apple event on the system Birthdays calendar also gets the 🎂 prefix and, when the birth year is known, the `Turns N` line. The year comes from the contact (`EKEvent.birthdayContactIdentifier` looked up as a `CNContact`, read-only), only for birthday events, asked through the Contacts prompt the first time Stark loads a birthday from a calendar the owner shows (the lookup runs in `AppleOverlayModel` after the filtered snapshot is published, so the first load never waits on Contacts; years are cached in memory per contact for the session, one lookup at a time, year-less contacts asked again when the app comes to the front; hidden calendars never reach Contacts); the year is used only to compute the age and is never stored or sent. Denied, limited or unmatched means the cake only. Info.plist `NSContactsUsageDescription`: "Stark reads the birth year of the people in your Birthdays calendar, only to show their age. It is never stored or sent anywhere." Apple events tagged `%birthday` by hand still show no age (series master has no original start year here); Mac Catalyst needs the Contacts resource-access build setting before it shows ages. Spec `docs/superpowers/specs/2026-11-17-birthday-cake-and-age-design.md`.

**Mac Catalyst target** (`CalendarSidebar`; issue #100): the app also builds and runs as a Mac Catalyst destination of the same `Stark` target (`SUPPORTED_PLATFORMS` includes `maccatalyst`, `TARGETED_DEVICE_FAMILY = "1,2"` — Catalyst requires the iPad idiom even though no iPad-specific layout exists). `StarkKit` and almost every view are shared unchanged; the only differences are gated by `#if targetEnvironment(macCatalyst)`, the first platform-conditional code in this codebase. On Mac, `ContentView` wraps its content in a `NavigationSplitView` with `CalendarSidebar` (a `List` selecting `CalendarMode` directly) instead of a plain `NavigationStack`, and both `ContentView` and `YearView` omit `ModeHandle` — its drag/tap gesture has no pointer/hover affordance, so the sidebar is the Mac-appropriate replacement for switching week/month/year. `CustomRepeatView`'s interval/unit pickers likewise swap `.pickerStyle(.wheel)` (an iOS `UIPickerView` touch-flick control) for a `Stepper` + `Picker(.menu)` on Mac; both branches still write the same `RecurrenceRule` fields. The window has a `480x520` minimum size (`StarkApp`, `.windowResizability(.contentSize)`) since the grid's fixed-height rows don't shrink with the window. ~~**Storage is local and independent per platform** — the Mac and iPhone builds show different data~~ (superseded 2026-11-15: both builds show and write the same Apple Calendar and Reminders data, synced by Apple; only Stark's sidecar (and, unread since phase 3, the old `.ics` files) stays per device; Stark itself still adds no shared/iCloud storage of its own, decision 2026-09-23; issue #100 closed). Distribution: Mac Catalyst is a second destination of the existing `com.caritos.todo-txt` App Store Connect record (Universal Purchase), not yet submitted.

**`OccurrenceExpander` keeps the anchor's time-of-day when it fast-forwards to the range**: the original fast-forward set `candidate = range.lowerBound`, so every occurrence carried the *range's* time (a 09:30 weekly reminder came back at 12:00 or 00:00) and the day/month/year differences used for `interval > 1` were computed from the wrong time, producing wrong-parity days (interval-2 daily/monthly/yearly). It now fast-forwards to `lowerBound`'s day at the anchor's time. Related trap: `DateMath.date(from:)` returns local **noon**, and `AgendaWindow`'s bounds used to be built from it, so `buildAgendaItems`' `displayRange.contains` silently dropped events before noon on the first day and after noon on the last. `range(around:)` and `loadRange(around:)` now run from the *start* of the first day to the last second of the last day (`startOfDay(day + 1) − 1 s`, stepped with a gregorian `Calendar` so DST days stay correct); never build inclusive day-range bounds from `DateMath.date(from:)`. Coupling to keep in mind: the future-range shortcut in `densityCounts` (`AgendaDensity.swift`, used by `gridDensity`/`yearDensity`) is only valid while `buildAgendaItems` uses `today` solely for the overdue cut-off/lookback; keep `YearDensityTests`' equivalence cases (which include interval > 1, count, until and non-noon anchors) in sync with any change there.

**Apple overlay and write-through** (2026-11-15; specs `docs/superpowers/specs/2026-11-15-apple-overlay-design.md` and `2026-11-15-apple-write-through-design.md`, spikes `2026-11-15-eventkit-write-spikes.md`): Apple Calendar and Reminders are the source of truth. Access is required: the overlay is always on (`AppleOverlayModel.isEnabled`), and while access is not granted `ContentView` shows `AccessRequiredView` above the grid (ALLOW ACCESS asks only from there; denied/write-only offers iOS Settings), nothing else shows (Stark keeps no items of its own since phase 3) and Add is disabled. Reading: the single merge point is `mergeAppleItems` (snapshot in, synthetic `AgendaItem`s out, ids `apple-...`); `agendaWithApple` merges THEN applies plans (agenda, grid and year densities use it). One shared fetch window (`AppleFetchWindow`, the hull of the registered display/grid/search/planner/weeklyReview ranges) feeds the snapshot, `LatestReloadGate` makes a superseded reload wait for the newest fetch, and every write Stark makes reloads the overlay itself (`refreshAfterWrite`; `EKEventStoreChanged` is unreliable after a save). Apple reminders get the 90-day overdue lookback; date-only reminders behave as all-day; every open reminder is fetched (dated ones outside the window too). Undated reminders are not in the agenda: Search and the planner's NO DATE pane (`TrayPane.panes(for:)`) list them, a planned one appears on its planned day, the editor shows "No date" and Add Date (date-only, today). Writing: views call `ItemRouter` (Apple-only since phase 3, 2026-11-17: an id without the `apple-` prefix is refused with an `ItemRouterError`); new items go to Apple, in the default calendar/list (`DefaultDestinationModel`, Settings > Apple Calendar and Reminders, writable ones only; the default and any picked destination are always shown; since 2026-11-17 the Settings pickers show each calendar's account under its title, warn when the current default is local-only (`AppleCalendarInfo.isLocalOnly`, `DestinationLabel`), the Add screen posts "Added to <calendar> · <account>"). Edit loads the real item (`router.details`) and writes a patch of only the changed fields diffed against `ItemDetails.formBaseline()`, never a stand-in saved whole; series edits go to the master (`.futureEvents`); a repeat Stark cannot represent is read-only text ("Custom, set in Calendar") and blocks converting; a rule change that would drop occurrences edited in Calendar asks first. Read-only: `AgendaItem.isReadOnly` = Apple source on a non-writable calendar; invitee-only events open read-only too (`AppleEditorState`); the read-only detail offers Open in Calendar/Reminders. Reminders: completing a repeating one is Apple's (EventKit advances it and leaves a completed copy; `complete` is idempotent per occurrence day); no Skip and no History for Apple items; uncompleting a series' completed copy is a notice only (`UncompleteNotice`). Events: Remove This Occurrence deletes that occurrence (`.thisEvent`); attended/skipped marks saved earlier live in the sidecar (`Library/Application Support/Stark/sidecar.json`, `ItemSidecar`) but can no longer be set and are not shown (see Event attendance). The sidecar also holds plan blocks for Apple reminders and, unused but decoded and re-encoded unchanged, the phase 2 import record (`importLedger`, `importedAt`), so older TestFlight builds (2.0.33 to 2.0.36) do not offer the import again; a file with a newer version is refused, never overwritten. Convert = create the other kind in the default destination + delete the original + remap plans (asks first when the event has attendees). Search: Apple events within +-2 years (registered only while Search is open), one row per series; all open reminders and completed ones in that window. Planner: Apple reminders in the tray, Done and saves through the router, a block whose occurrence the series has moved past reads DONE. Weekly Review: Apple reminders by completion day. Tag suggestions read the loaded snapshot. Day export includes Apple items because it exports what the agenda shows. Stark writes no `.ics` files and makes no network call unless Weather is switched on. Never prune the selection while access is not granted or the calendar list is not loaded. **Import of Stark's own items** (phase 2, 2026-11-17, spec `docs/superpowers/specs/2026-11-17-apple-import-phase2-design.md`): removed in phase 3 the same day, after the gate on the owner's phone found nothing left to import. `ImportStarkItemsView`, `ImportModel`, `ImportPlanner`, the Settings row and the "Not imported" mark are gone; the old `.ics` files stay in Documents, untouched and no longer read, until the app is deleted. How the import worked is in that spec and in CLAUDE.md's phase 2 log.

**Quick add (2026-11-18)**: `QuickAddParser` (Kit, `Planner/QuickAddParser.swift`, pure, anchored English rules driven by a `Calendar`; not `NSDataDetector`, which cannot take a fixed now) reads a typed Add title for a day, clock time, "for N hours", repeat and a leading "remind me to" / "todo:". `QuickAddRow` (app) shows one button with the summary under the Title field while the parse is non-nil; tapping it (never automatic) sets title, date, end (suggested end, else start + default duration), All day (when the suggestion has no time, any kind; a reminder's Due picker hides its time and midnight already means date-only through `FormFields.dueHasTime`), repeat, and kind (reminder when suggested; an event suggestion keeps the current kind). The end is pre-shifted because the Starts picker's `onChange` moves the end with the start. Nothing recognised, or only a date with no title, shows no row. Spec `docs/superpowers/specs/2026-11-18-quick-add-design.md`.

**Weather (2026-11-18, opt-in, off by default)**: Settings > Weather > Show weather.
