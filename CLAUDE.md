### sim.sh build behavior

`sim.sh` always builds the **Release** configuration for both simulators and USB-connected physical devices — there is no Debug/dev-client picker. This means every local build is Metro-free: the simulator path installs and launches the built `.app` directly via `simctl`, and the device path installs and launches directly via `devicectl`, with no "Development servers / npx expo start" screen and no Metro dependency at all.

**Release builds are always a full clean build, never incrementally reused** (`mobile/scripts/sim.sh`, the DerivedData-staleness check). `expo-dev-client`'s podspec links `expo-dev-launcher` only for the `Debug` pod configuration (`:configurations => :debug`) — a genuinely fresh Release build never includes the dev-client launcher and boots straight into the app (verified: a fresh Release `.app` has zero `EXDevLauncher` symbols/resources, and installing+launching it lands directly on the Calendar screen). The bug this guards against: an incrementally-reused Release build in DerivedData can be a stale artifact cached from before some pod/config change, silently still carrying the old (possibly dev-launcher-linked) binary — `Podfile.lock`'s mtime alone isn't a reliable signal that a cached build still reflects the current pod graph. If DerivedData is missing (e.g. after running `cleanup-disk-space.sh`) or `Podfile.lock` is newer than the last build, `sim.sh` runs `xcodebuild clean build` automatically; no manual intervention needed.

`sim.sh` bumps `app.json`'s `ios.buildNumber` on every local build so Settings' "vX.Y.Z (N)" reflects the build actually installed. This is an EAS-independent counter — `appVersionSource: "remote"` in `eas.json` means EAS ignores this field and manages its own build number for TestFlight/App Store builds (`ship.sh`), so the two numbers are expected to diverge; `ios.buildNumber` only ever tracks local sim/device installs.

`sim.sh` only targets simulators and USB-connected physical devices — it does **not** offer a TestFlight/EAS-cloud-build option. A dev-client build (`developmentClient: true` in `eas.json`) requires the Xcode Debug configuration, which compiles React Native's `RCTKeyCommands.m` (`#if RCT_DEV`) into the binary. That file calls the private `UIEvent` selectors `_isKeyDown`, `_modifierFlags`, `_modifiedInput` to support hardware-keyboard dev-menu shortcuts — Apple's App Store Connect binary validator rejects any upload referencing them, so dev-client builds can never pass TestFlight/App Store submission, independent of SDK image version. Use `ship.sh` (the `production` profile — Release config, no dev client) for anything that needs to reach App Store Connect or TestFlight.

**Both `sim.sh` and `ship.sh` verify local (`file:`) `package.json` dependencies before building** — e.g. `expo-icloud-file` at `mobile/modules/expo-icloud-file`. This class of bug has two distinct failure modes and each script guards against the one it can actually hit: `sim.sh` builds locally against whatever `node_modules` already contains, so it checks that every `file:` dependency actually resolves to a symlink in `node_modules` — seen in practice: `node_modules` existed and looked otherwise complete (from an `npm install` run before the dependency's target directory existed, or some other install-ordering quirk), but the symlink for `expo-icloud-file` specifically was missing. A missing link means the native module never autolinks into the Pods project, which produces **no build-time error at all** — the app builds and launches fine, and the failure only surfaces the first time JS calls into the module, as `Cannot read property 'readFile' of null` (`NativeModules.ExpoIcloudFile` is `undefined`). If `sim.sh` finds a missing link it runs `npm install` to restore it, then forces `pod install` regardless of `Podfile.lock`'s mtime (which doesn't change just because `node_modules` did, so the existing staleness check would otherwise miss this case). `ship.sh` builds on EAS's cloud infra, which always does a fresh install from the lockfile — a missing local symlink can't reach it — so instead it checks that every `file:` dependency's *target directory* still exists on disk, catching a stale entry left pointing at a deleted directory (the "dangling `file:` dependency" class of EAS build killer — see the global CLAUDE.md notes on Local `file:` package.json dependencies and EAS builds) before spending a build credit on a failure that's obvious from the repo alone. Both checks hard-fail immediately if a dependency's target directory is missing entirely — that's a stale `package.json` entry, not something `npm install` can fix.

## Shared Layer

**Pure transform pattern** — every command is a pure function: `Task[]` in, result out. No I/O, no console output, no `process.exit`.

**Error handling** — transforms throw `Error` with a plain message. Callers (mobile) catch and shows an inline error or alert. `process.exit` never appears in shared code.

**`@shared/*` alias** — mobile imports shared code via `@shared/parser`, `@shared/commands/focus`, etc., resolved by Metro (watchFolders) and babel-plugin-module-resolver.

## Native iOS App (`ios/`)

**What it is**: the native Swift/SwiftUI app, which replaced the deprecated Expo app in `mobile/` (same bundle id `com.caritos.todo-txt`, same App Store listing). Design: `docs/superpowers/specs/2026-09-17-stark-native-rewrite-design.md` (+ `2026-09-18-recurrence-picker-design.md`). It has its own data model (separate `Event` and `Reminder` types, iCal priority 1–9) and **does not read `todo.txt` at all** — there is no migration path yet, so shipping it as-is would start every existing user on an empty calendar. Two parts, same split as the author's `spool` project: `ios/Sources/StarkKit` (SwiftPM package holding *all* testable logic, tested with Swift Testing — `import Testing`, `@Test`, `#expect`, not XCTest) and `ios/App/Stark` (thin SwiftUI views, verified by building and by running on a simulator/device — never put logic in a view; if it can be tested, it goes in StarkKit).

**Storage**: local Documents directory only — no iCloud storage is planned (decision 2026-09-23). `recurring.ics` holds every recurring Event/Reminder and is always loaded in full; `YYYY-MM.ics` holds each month's one-offs plus completion records. Recurrence is standard `RRULE`/`EXDATE`. `PlannerFile` queues a failed save to `Library/PendingWrites` (coalesced per file) and retries on launch/foreground; a missing file means "no items yet", a genuine read failure throws and is never treated as empty. Stark's own files hold only Stark's own items, and since 2026-11-15 they receive no NEW items: **Apple Calendar and Reminders are the source of truth** (write-through decision, spec `docs/superpowers/specs/2026-11-15-apple-write-through-design.md`). Phase 1 (2026-11-15) built the write path (merged to main and shipped to TestFlight as v2.0.24 (build 26) on 2026-11-15): every new item (Add screen; until 2026-11-17 also the Claude Code bridge) is created in Apple through EventKit, Apple items are edited/completed/deleted in Apple through `ItemRouter` -> `AppleItemRepository`, and Stark's older `.ics` items are still shown and edited in these files through the same router until phase 2 imports them into Apple; phase 3 then removes this store. Apple items are never copied into these files; what Apple cannot hold (plan blocks for Apple reminders, attended/skipped marks on Apple events, the phase 2 import ledger) lives in one JSON sidecar, `Library/Application Support/Stark/sidecar.json` (`ItemSidecar`). Access to Calendar and Reminders is required (`AccessRequiredView`). See "Apple write-through log" below.

**Agenda architecture — views never expand recurrences.** `buildAgendaItems` (`Planner/AgendaBuilder.swift`) → `groupAgendaByDay` (`Planner/AgendaDays.swift`) are the single source of truth for what the agenda shows. Two ranges in `AgendaWindow`: the *display* range (`range(around:)`, today −14 … +60) and the *load* range (`loadRange(around:)`, adds the 90-day overdue lookback). Display must always be a subset of load, and **anything that moves the window must `store.loadMonths(covering:)` first** or items in unloaded month files silently vanish (this drift bug happened once already). **Every calendar day in the display range gets a header, empty or not.** An earlier version only created sections for days with items, so tapping a month-grid day landed on the next day that had items (or the window edge) — "wrong date". Tapping a day outside the window re-centres `agendaAnchor` (and loads its months) instead of clamping.

**The window follows the calendar past midnight** (`AgendaWindow.refreshedAnchor(current:lastSeenToday:now:calendar:)`, a pure function, tested including DST and timezone-shift days): `ContentView` holds `today` as `@State` and passes it to `MonthGridView` and `AgendaView` (neither calls `Date()` itself, or a view left open overnight would keep showing yesterday as "today"). On `scenePhase == .active` and on `UIApplication.significantTimeChangeNotification`, if the calendar day changed *and* the agenda was still following today (anchor's day == last-seen today), `followCalendarDay()` loads `loadRange(around: newToday)`'s months first, then moves the anchor, selection and scroll to the new today. If the user had deliberately re-centred elsewhere, the anchor is left alone. Not verified: a real midnight rollover, or a timezone change while running (`TimeZone.current` is cached in-process, so a timezone-only change may not be noticed until relaunch).

**Overdue and completion semantics** (mirroring the Expo app): overdue is day-granular. An incomplete reminder occurrence before today is pinned to today's section with `isOverdue` and keeps the missed date/time in `occurrence` (the row shows it in the accent colour, e.g. "Sep 19 at 6:00 AM"). One-offs are shown as-is. **A recurring reminder shows a single open row carrying its *first* (oldest) un-resolved miss in the lookback window — daily series included** (no longer "latest miss" / "daily dropped"); today's own occurrence is folded into that row, not shown separately. The row's time line reads e.g. "Sep 19 at 6:00 AM · 3 days overdue" (`AgendaItem.daysOverdue(today:)`, `OverdueLabel.text`, capped at "90+ days"; `today` comes from `AgendaView`, Search/Weekly Review rows pass none and show no suffix). Events are never overdue. Resolving the carried row with `completeReminder`/`skipReminder` also exdates every later un-exdated miss and today's occurrence (`PlannerStore.carriedOccurrences`; only when the resolved occurrence is on or after the lookback start, so a miss older than the lookback, e.g. one handed over by Weekly Review, resolves just that one occurrence), so a series missed three times takes one tap to clear and nothing resurfaces the next day. **While a recurring reminder has an open row (a miss, or today's occurrence not yet done) its later occurrences are not listed at all** (issue #107, decided 2026-10-20), and when nothing is open only its single NEXT occurrence is listed, never the whole run of future days (a daily reminder is one row, not sixty); the following one appears only once that is completed or skipped. Month/year density dots follow the same rule. **Only misses after the series' latest completion count** (`buildAgendaItems`: a tick closes every earlier gap, which stays visible as a gap in the History section), so completing today's occurrence from Search also clears the carried row; skipping today's leaves it open. Completing a recurring occurrence exdates it on the master and appends a separate one-off completed copy; `uncompleteReminder` flips that copy back open (the master keeps its exception date, so nothing shows twice). Skip is exception-date only. Completed reminders are shown in the agenda on their due date. **Apple reminders are shown overdue at any age** (`mergeAppleItems`, fix 2026-11-17: an open Apple reminder due before today is pinned to today with its real due date in `occurrence`; the 90-day lookback applies to Stark's own items only). (All of this paragraph is the LOCAL store's semantics; Apple reminders follow Apple's rules: see "Behaviour changes for the owner" in the Apple write-through log.) **`completeReminder` is idempotent** (a no-op for an unknown id, an already-completed one-off, or a recurring master that already has an exception on that calendar day), so any two paths resolving the same occurrence — the checkbox timer firing after Done/Skip in the detail sheet, a double tap — can't produce a second exception date or a second completed copy. That guarantee lives in the store, not in the app layer (an earlier version guarded it in `StarkApp`, untested); the `PendingCompletions` commit closure is `router.complete(id:on:)` (`StarkApp`; since 2026-11-15), which sends Stark's own ids to `store.completeReminder` and Apple ids to EventKit with the occurrence's own date.

**Per-feature behavior notes** are in `docs/ios-feature-notes.md` (moved out of this file 2026-11-12). Read the matching paragraph before changing one of these features: Completion history; Checkbox; Event attendance; Converting an event to a task and back; Last day of the month; Month grid density is two 1 pt lines under each day number; Week / month / year modes with a drag bar; Scroll-synced calendar selection; Search; Timeboxing / Plan view; Week planner and past days; Weekly Review; Claude Code bridge (removed 2026-11-17); Apple overlay and write-through; Settings; Tag autocomplete; Repeat End and event URL; Birthdays and anniversaries; Mac Catalyst target; `OccurrenceExpander` keeps the anchor's time-of-day when it fast-forwards to the range.

**Row hit-testing — never nest Buttons in a `List` row** (`App/Stark/Stark/AgendaRow.swift`, `AgendaRowTargets`): the row's visuals are drawn non-interactive, and two *sibling* `.plain` Buttons partition the row — a 44 pt checkbox strip and "everything else" — so no tap can be claimed by both and no gesture-priority rule is involved. A Button inside another Button's label does not work, and a `List` row's default button style turns the whole row into one target; that is exactly why the checkbox originally opened the detail sheet instead of completing. Verified on a real iPhone (2026-09-20).

**Theme/UI rules** (Fantastical look since 2026-11-15, staged redesign, spec `docs/superpowers/specs/2026-11-15-fantastical-visual-design.md`): `Theme.swift` has adaptive `Colors` (light/dark from `Color(light:dark:)`; `background` is the grouped ground, `card` the white/dark card, one blue `accent`, `eventDot` purple until stages 2-3), `Spacing` and `Fonts.mono` (name kept; it now returns the system font with monospaced digits; JetBrains Mono was removed). Nothing forces a colour scheme: the app follows the phone. No hardcoded colours in views except an Apple calendar's own colour. Forms and settings are `insetGrouped` lists with `Colors.card` rows on `Colors.background`; toolbar buttons (`SquareToolbarButton`/`SquareButton`, names kept) are round, the save button accent-filled; text on accent fills is white. The planner's time-accurate blocks keep square edges. Editing a recurring item changes the whole series (single-occurrence overrides / `RECURRENCE-ID` are deliberately not implemented). The old Braun/Bauhaus rules (dark, hard edges, orange accent, mono font) apply to `mobile/` only.

**Testing and deploying** (the user prefers a real device — it's faster than a simulator boot and is the only place touch/hit-testing bugs show): `swift test` for StarkKit; `ios/App/deploy.sh` builds, installs and launches on the paired iPhone (installs over the App Store build's bundle id; their `todo.txt` is untouched). Only deploy a coherent, verified build. To inspect what the app saved, pull the container back with `xcrun devicectl device copy from --domain-type appDataContainer --domain-identifier com.caritos.todo-txt --source /Documents …`. On the simulator, `simctl` can build/install/launch/screenshot but cannot tap; **`idb ui tap` does work** (Maestro 2.0.2 failed to start its iOS driver on this setup). `idb_companion` prints the entire shell environment (tokens included) when invoked — always redirect its output and never paste it.

## Key Invariants

- `verbatimModuleSyntax: true` — use `import type` for all type-only imports (all layers).
- Completed tasks have no priority (stripped by `serializeTask` when `task.done = true`).
- Typed tasks (`type:event`/`birthday`/`anniversary` — anything with `task.extensions['type']` set) never carry a priority — this is a deliberate product decision (issue #66), not an oversight. `AddTaskModal`'s Priority group only renders when `addType === 'task'`, and `handleAdd` defensively re-checks `addType === 'task'` before applying the picked priority (state persists across the TASK/EVENT toggle even though the UI hides it). `task/[line].tsx`'s Priority section only renders when `!task.extensions['type']`. Don't re-add priority to either screen for events without confirming first — it was added once already and reverted for exactly this reason.
- Extension regex `([^/\s]\S*)` intentionally excludes URL schemes — values starting with `/` are not captured as extensions (prevents `http://` from matching as `http: //`).
- `matchesFilters()` in `shared/commands/list.ts` is exported and reused by mobile.
- `today()` returns the **local** calendar date (not UTC) — in `mobile/src/utils.ts`.
- `nextWeeklyDate` in `shared/commands/focus.ts` accepts an optional `frequencyDay` param (e.g. `"W,F"`). When present, it finds the next calendar date that falls on one of those weekdays rather than advancing by 7-day intervals.
- `focusSortKey` skips the `last-done` cycle check for `frequency-day` tasks. For those tasks `applyDone` already advances `start:` to the next valid weekday, so `last-done` will always precede `currentOcc` — applying the 7-day cycle window would incorrectly jump to the occurrence after next (e.g. showing Monday when Friday is correct).
- `applyDone`'s recurring-task branch appends a new completed "copy" `Task` (the `x <date> ...` line recording this occurrence) with `line: tasks.length + 1` — never a placeholder like `line: 0`, matching `applyAdd`'s convention for appended tasks. Mobile's `TaskContext.save()` sets React state directly from whatever a shared transform returns, with no re-read/renumber in between saves. A placeholder line number here would let two completed recurring tasks collide on the same `line` value within one app session, which several mobile screens key list rows by (`key={task.line}`, `done-${t.line}-${date}` in `calendar.tsx`) — a duplicate-React-key crash (issue #61).
- `done` advances `start` to the next scheduled occurrence for `frequency:weekly`, `frequency:monthly`, and `frequency:daily` tasks. `frequency:yearly` tasks are the exception — `start:`'s year is never advanced (only `last-done` changes), since yearly occurrence math (`nextYearlyDate`) only needs `start:`'s month-day, not its year, and freezing the year preserves the original birth/anniversary year for age calculation (`computeYearCount`) and for `every:N>1` multi-year cycling (which needs a fixed anchor year).
- Recurring occurrence dates (`nextYearlyDate`, `nextMonthlyDate`, `overdueOccurrenceDate`, `resolvePositionalDay` in `shared/commands/focus.ts`) always clamp the day-of-month to the last valid day of the target month via `daysInMonth()` (`shared/utils.ts`) — e.g. a `start:` day of 31 in a 30-day month becomes day 30, Feb 29 becomes Feb 28 in non-leap years. This prevents a raw invalid date string (e.g. `2026-06-31`) from being interpreted differently by different screens (native `Date` parsing silently overflows it into July 1, while raw string comparisons don't).
- `nextMonthlyDate` and `overdueOccurrenceDate` build their day-of-month candidate `Date` at **noon** (`new Date(year, month, day, 12, 0, 0)`), matching the noon timestamp used for `today`/`t` (`new Date(todayStr + 'T12:00:00')`) — never construct one at local midnight and compare it against the other at noon. A midnight-vs-noon mismatch makes a same-calendar-day candidate register as "already passed" (`candidate < t`) purely from the time-of-day difference, not the actual date. This caused issue #74: right after completing a monthly task, `applyDone` advances `start:` to next month and stamps `last-done` with today; on the next render `effToday()` (`applyFocusForWindow`) substitutes that new `start:` as a fake "today," and the midnight/noon mismatch then misjudged that future date as already-due, resurfacing the just-completed task on today's list labeled with its own future due date (e.g. "due Aug 15" appearing the moment a July 15 occurrence was marked done). `overdueOccurrenceDate`'s monthly branch also now requires the candidate be *strictly* before `today` (`currCandidate >= t` returns null) to match its own doc comment and the weekly branch's `diffDays <= 0` → not-overdue behavior — a monthly task due exactly today and not yet completed is due, not overdue, until the day passes.
- `applyFocusForWindow`'s `sortKeyFor` (`shared/commands/focus.ts`) sorts overdue items by **date only** — never appends the task's start time-of-day. The calendar agenda row (`mobile/app/calendar.tsx`) always replaces an overdue item's time with a "due `<date>`" label, so a hidden time-of-day in the sort key produces a list position the user can never explain by looking at the row. This caused issue #76: a weekly task whose current cycle lands exactly on today (not yet done) is correctly flagged overdue with `overdueDate` = today, but its `start:` time-of-day (e.g. `T14:00`) got appended to the sort key, sorting it after same-day timed items instead of clustering with the other, earlier-dated overdue items at the top of the list — the bug was invisible for genuinely-overdue-from-an-earlier-date items only because their date alone already sorted them ahead of every today-dated item, time suffix or not.
- `skip` on a non-recurring task (no `frequency:` extension) removes it from the list instead of erroring. `applySkip` returns a `SkipResult` union: `{ removed: true }` or `{ removed: false; skippedDate; nextDate }`. For overdue weekly/monthly tasks, `applySkip` uses `overdueOccurrenceDate()` to add the actual missed occurrence date to `exdate` — NOT `focusSortKey` (which returns today for overdue tasks and would fail to advance past the missed occurrence).
- `add` and `event` inject `start:today` when no `start:` is provided. This makes new tasks appear in focus immediately.
- `focus` handles `frequency:yearly` via `nextYearlyDate` in `isInFocusWindow` and `focusSortKey` — without this, completed yearly tasks stayed visible in focus until the next occurrence's date passed.
- `focus` shows **overdue** tasks: regular tasks whose `start:` date is in the past, and recurring tasks whose most-recent scheduled occurrence hasn't been marked done. `overdueOccurrenceDate()` detects missed occurrences; their sort key is set to today so they sort to the top.
- `isInFocusWindow` never hides a recurring task/event based on how old its `start:` date is. A prior guard (commit `2de9411c`) hid daily/monthly/weekly-typed recurring tasks whose `start:` was more than 730 days old and had no `recur-until:`, meant to suppress stale ICS-imported multi-day workshops — but it also hid genuinely still-active long-running recurring tasks/events once they'd been running long enough (commit `599be66`). Recurring means recurring: age of the original `start:` must never suppress it. The `type:event` branch's `weekly` case now delegates to `nextWeeklyDate(...) <= windowEnd` (matching the `monthly`/`yearly` cases) instead of the old blanket `if (frequency) return true`, which had ignored the window entirely for typed weekly events. `nextWeeklyDate`'s `frequency-day` search also anchors at `max(start, todayStr)` rather than always `todayStr`, so a task created today whose first occurrence is a later date can't match an earlier same-weekday date that falls before its own `start:`.
- **Task line numbers** are 1-based positions in the non-empty task list (blank lines stripped by `readTasks`). They renumber on every read — `task.line` is display position, not a stable ID.
- `cleanTitle()` strips todo.txt extensions from task text for display. It is defined **inline** in each screen file — it is not exported from a shared module.
